# `postgres`

The financial record's database on the reference cloud (RDS for PostgreSQL, `PHASE_15_PLAN.md` C1 and C3). Called by each
environment root. **Never applied**: there is no account in Phase 15, so every property below is asserted by
`tests/postgres.tftest.hcl` over a plan against a mock provider. That proves the configuration, not RDS's behaviour. The
engine version, instance classes, windows and retention values are unverified against the service.

The security properties are literals in `main.tf`, not variables, so no environment can turn one off.

## What it builds

| Property | Held by the run |
|---|---|
| PostgreSQL at the pinned major, with a synchronous standby in another zone | `the_database_has_a_synchronous_standby` |
| TLS required by the server (`rds.force_ssl = 1`), through a parameter group the instance really uses | `the_database_accepts_tls_alone` |
| `max_connections` is the value the root gives, set once, applied `pending-reboot` | `max_connections_is_the_value_given_and_waits_for_a_reboot` |
| Volume and Performance Insights encrypted under the given customer-managed key | `the_volume_is_encrypted_under_the_given_key` |
| No public address; on the given (workload) subnets | `the_database_has_no_public_address_and_lives_on_the_given_subnets` |
| Its own security group: port 5432 from one given security group, no CIDR | `only_the_given_security_group_reaches_the_port` |
| The master password generated by RDS and kept in Secrets Manager under the given key, so no value reaches state | `the_master_password_is_generated_and_kept_out_of_state` |
| Point-in-time recovery; automated backups kept when the instance goes; a final snapshot | `point_in_time_recovery_is_on_and_outlives_the_instance` |
| Deletion protection; no major version move and no change outside the maintenance window | `the_database_cannot_be_deleted_by_a_plan` |
| A backup vault under its own key, a daily snapshot, and a copy to a vault across an account or region boundary | `the_vault_is_under_its_own_key_and_every_snapshot_is_copied_across_the_boundary` |
| Malformed input refused: fewer than three zones, the database's key on the vault, an alias, a copy inside the boundary, under a week of recovery | the `..._refused` runs |

`aws_db_instance` and `aws_backup_vault` carry `prevent_destroy`, and `TerraformIsPinnedAndCheckedTest` refuses either
without it, and refuses a database given `password`.

## `max_connections` has one source

The number is written once in the repository: `FINAPP_DB_SERVER_MAX_CONNECTIONS` in `deploy/overlays/<environment>/kustomization.yaml`,
the literal the application reads and the manifest policy's connection budget counts. Each root parses that file and
passes the value here, and each root's test parses it again and compares it with the planned parameter. A literal
missing, given twice or not a number stops the plan.

**It is static on the engine.** RDS applies it only when the instance restarts, and rejects `immediate` for it. After an
apply the parameter group holds the new value, the instance reports `pending-reboot`, and **a plan shows nothing**, so
nothing but the sequence below makes the two sides agree. `ConnectionPoolSizingGuard` checks the declaration and cannot
read the server.

- **Raising it**: merge the overlay's change. Apply Terraform, reboot the instance in a window (on Multi-AZ, a reboot with
  failover is the shorter interruption), confirm with `SHOW max_connections`, and only then roll the application.
- **Lowering it**: merge, roll the application first so the fleet's pools shrink, confirm the peak in `pg_stat_activity`, then
  apply and reboot.

Either order the other way round leaves a window where the application's budget is false. The 12 reserved connections
(`FINAPP_DB_RESERVED_CONNECTIONS`) must also cover RDS's own administrative sessions, which are counted against this
number.

## The separate key

**The entry asked for backups under a separate key, and RDS does not offer that within an account and region.** RDS's
automated backups and its snapshots are encrypted with the instance's key. AWS Backup's table of independently encrypted
resources lists RDS as not supported: a vault's key does not change an RDS recovery point. A copy that crosses an
account or a region does take the destination vault's key. What this module therefore builds, and what it does not:

| What | Key | Point-in-time? |
|---|---|---|
| Automated backups (35 days at most) | the **storage** key: no setting exists | yes |
| Daily snapshot in this module's vault | the storage key, whatever the vault's key is | no |
| Its copy in `backup_copy_vault_arn` (another account or region) | **that vault's key** | no: a copy is a snapshot, so its recovery point is the schedule |

`backup_kms_key_arn` is still required and is refused if it equals the storage key. The vault's own key protects what
AWS Backup itself encrypts. It is not what stands between the storage key and the backup. The destination vault is an
input because no such account exists: `THREAT_MODEL.md` §6 item 23 holds the choice, with the recommendation. Replicating
automated backups to another region would keep point-in-time recovery under another key, and is Phase 16's
(ADR-0121 follow-up).

A key's own policy must admit the service that uses it (`RDS`, `backup.amazonaws.com`), and a cross-account copy needs
the storage key to admit the destination. Those policies are the security module's.

## Inputs and outputs

Inputs: `name_prefix`, `region`, `account_id`, `vpc_id`, `private_subnet_ids_by_zone`, `client_security_group_id`,
`instance_class`, `allocated_storage_gib`, `max_allocated_storage_gib`, `max_connections`, `storage_kms_key_arn`,

Outputs: `identifier` and six that read the plan back for the roots' tests. See `variables.tf` and `outputs.tf`.

## Operating it

- **Who connects**: the security group admits the cluster's nodes, so every pod on a node reaches the port. The namespace's
  NetworkPolicy narrows that to the application, and the database's own roles do the rest.
- **The master user** (`finapp_master`) is for the one-time bootstrap step alone (`DATA_MIGRATIONS.md` §2.2). Its secret
  is RDS's; nothing in this repository reads it.
- **Restore**: a managed point-in-time restore is deferred with every apply (`PHASE_15_PLAN.md` §1.1). The local restore
  rehearsal and its financial verification are `OPERATIONS_RUNBOOK.md` §11.5's. On a real database, a restore makes a **new** instance, so
  the parameter group, security group and subnet group must be re-attached before anything connects, and it comes up
  with the application's `max_connections` only once it is using this parameter group.
- **Before relying on this**: run the checks (`OPERATIONS_RUNBOOK.md` §11.13).

## What it does not do

No KMS key, no role inside PostgreSQL (`P15-TSK-004`'s bootstrap step), no application credential, no read replica or
cross-region copy (Phase 16), no connection pooler (Phase 16, by measurement), no apply.
